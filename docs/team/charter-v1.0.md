## 1. 团队价值观
- **透明沟通**：进度公开，遇到困难或阻塞绝不隐瞒，尽早向团队求助。
- **质量至上**：拒绝“能跑就行”的代码，必须通过自动化测试和代码评审（Code Review）才能合并。
- **互相尊重**：技术讨论对事不对人，乐于分享知识，共同成长。
- **拥抱变化**：面对需求变更或技术重构，积极应对，不抱怨。

## 4. 开发与 Git 规约
- **主干保护**：`main` 分支受保护，严禁直接 `git push`，必须通过 Pull Request (PR)。
- **分支命名**：`feature/功能名`（如 `feature/qa-question`）、`fix/bug名`（如 `fix/vote-bug`）、`docs/文档名`。
- **提交信息 (Commit Message)**：遵循 Conventional Commits 规范（`feat: 新增投票功能`、`fix: 修复采纳状态错误`、`docs: 更新API文档`）。
- **代码风格**：Java 遵循 Google Java Style，前端使用 ESLint + Prettier 严格格式化。

## 5. 完成的定义 (Definition of Done, DoD)
一个任务（Task）或用户故事（User Story）只有满足以下所有条件，才能在看板上移至 `Done` 列：
1. 代码已实现且符合需求（本地运行无误）。
2. 编写了相应的单元测试，且全部通过（`mvn test` 绿）。
3. 代码已推送到功能分支，并发起了 PR。
4. 至少 1 名其他队友进行了代码评审（Review）并留下 LGTM (Looks Good To Me)。
5. CI 自动化流水线通过，且成功合并到 `main` 分支。
6. 看板卡片已更新至 `Done`。

## 6. 冲突解决与纪律
- 技术方案出现分歧时，先通过查文档/做原型测试验证；若仍有分歧，由 PO 和 SM 协商拍板。
- 严禁在 `main` 分支上强行合并（Force Push）或删除队友的未合并分支。
- 连续 2 次无故缺席重要会议（站会除外），需在下次会议上面向团队说明原因。
