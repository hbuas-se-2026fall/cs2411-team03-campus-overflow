# ADR-009：渐进式质量门禁

**状态**：Sprint 3 已完成，门禁转为阻断 ｜ **驱动特征**：可持续集成、可演进性（硬约束）

## 背景

起始代码的领域层/应用层存在 107 个 `TODO(Sx)` 方法，随之有约 38 个测试处于失败状态（测试即需求规格）。如果 CI 原样运行全量测试，develop 分支会在实现完成前连续数周红灯，而分支保护的"必须通过状态检查"会阻止一切合并；若为此关闭检查，又失去了 CI 的意义。

## 决策

按 Sprint 范围**逐步扩大**必须通过的测试集合，而不是一上来要求全绿：

| 门禁 | S0 | S1 | S2 | S3 | S4 |
| --- | --- | --- | --- | --- | --- |
| 编译 + ArchUnit | 必须绿 | 必须绿 | 必须绿 | 必须绿 | 必须绿 |
| 单元测试范围 | 共享内核、Identity | + Q&A | + Reputation | 全部模块 | 全部模块 |
| 领域覆盖率 | — | co-qa-domain ≥ 70% | + co-reputation-domain ≥ 70% | 根 POM 0.70 | ≥ 70%（挑战 80%） |
| 应用层测试 | — | Q&A 已有 + 新增 | + Reputation 自建 | + Discovery 自建 | 全部 |
| 集成测试 | 允许失败 | 允许失败 | 允许失败 | 必须绿 | 必须绿 |
| 前端构建 | 必须绿 | 必须绿 | 必须绿 | 必须绿 | 必须绿 |

实现方式：

1. CI 中通过环境变量 `SPRINT_MODULES` 限定单元测试与覆盖率门禁的运行范围（`mvn … -pl "$SPRINT_MODULES" -am`），每个 Sprint 计划会后由质量负责人更新。
2. 集成测试阶段在 S3 之前设置 `continue-on-error: true`，S3 移除该行使其成为硬门禁；本 Sprint 已执行移除，端到端与单元测试、覆盖率一样，失败即阻断。
3. 覆盖率阈值按模块在对应领域模块 `pom.xml` 中覆盖父 POM 属性 `domain.coverage.minimum`；S3 统一修改根 POM 为 0.70。

## 三个阶段的落地情况（Sprint 3 结项）

门禁不是一次性拉满，而是按 Sprint 分三步收紧——先让流水线跑起来（只告警），再守住领域层（阻断），最后收口到全量（阻断）：

| 阶段 | 门禁形态 | 阻断对象 | 实施方式 | 实际执行 |
| --- | --- | --- | --- | --- |
| **S0 只告警** | 编译 + ArchUnit 必须绿；单元测试只跑共享内核与 Identity | 无覆盖率下限，覆盖率只出报告 | 根 POM `domain.coverage.minimum = 0`，`jacoco check` 形同虚设 | 报告照常生成，红灯只提示不拦截 |
| **S1 领域层阻断** | 第一个领域模块达到 70% 即转为硬门禁 | `co-qa-domain` 低于 70% 直接失败 | 在 `co-qa/co-qa-domain/pom.xml` 中覆盖 `domain.coverage.minimum` 为 0.70，并自建应用层测试 | S1 结项时 qa 领域层达标，门禁生效 |
| **S3 全量阻断** | 根 POM 统一 0.70，所有领域模块、全量单元测试与端到端集成测试一律硬门禁 | 任一领域模块低于 0.70、任一步骤（含 `CampusOverflowFlowIT`）失败 | 根 POM `domain.coverage.minimum` 由 `0` 改为 `0.70`；`ci.yml` 删除 `SPRINT_MODULES`，单元测试与覆盖率阶段恢复全量执行，并删除集成测试阶段的 `continue-on-error` | 本 ADR 结项时四个领域模块全部达标；集成测试已转为硬门禁，当前因 `SearchIndexProjector`（#38）未实现而红（真实缺口，非 flaky） |

### 集成测试一并转为硬门禁

早期保留 `continue-on-error: true` 的理由是组织 Actions runner 未分配。仓库由私有改为 public 后 runner 正常分配，这一前提已消失，因此本 Sprint 删除该行，**S3 起端到端为硬门禁**：FlowIT 挂了 CI 就是红的，不再出现"失败但允许继续"的绿灯。

删除后暴露出两个此前被掩盖的事实，一并记在这里，避免后来者再被"绿"误导：

1. **`continue-on-error` 下的"success"是假象**。此前 CI run #12 的「集成测试」步骤结论显示 success，但打开该步骤日志可见 `DockerClientProviderStrategy` 报 `client version 1.32 is too old. Minimum supported API version is 1.40`，`CampusOverflowFlowIT` 实际是 ERROR——步骤之所以显示 success，是 `continue-on-error` 把失败按成功上报。也就是说端到端此前从未在 CI 上真正跑过。
2. **Docker 客户端 API 版本已修复**。托管 runner 的 Docker 引擎要求最小 API 1.40，而 Testcontainers 内置的 docker-java 默认发 1.32 的请求。新增 `backend/co-bootstrap/src/test/resources/docker-java.properties`（`api.version=1.44`，Docker 25+ 均接受）后，FlowIT 能在 CI 上真正启动 MySQL/Redis 容器并执行。

修复后 FlowIT 首次真正执行，暴露出一处**真实缺口**：`SearchIndexProjector` 仍是行走骨架（Issue #67 / PB-32 #38 未合入），`dis_search_doc` 没有任何写入，端到端场景里的"搜索命中"断言必然失败（`$.items[0].id` 在 20 秒内取不到值）。这不是 flaky，也不是本轮改动引入的回归，而是上游依赖未完成的真实红灯；门禁因此按设计保持红色，待 #38 合入后自然转绿。

本地 Docker 起不来的问题不影响该结论——端到端统一在 CI 执行。

### 仍然遗留的一项

**行走骨架未完全移除**。`NotificationProjector` 已在 PR #82 中实现并清理；`SearchIndexProjector` 仍是空实现（PB-32 / Issue #38 未合入），此时它是代码里唯一的搜索投影，删掉会让投影彻底断流，因此按 T3-09 的约定「队友的 PR 没合就先不合，别自己扛」，保留并在 PR 中登记依赖。该空实现同时是端到端集成测试当前红灯的唯一原因（见上节）。

## 红线（不得绕过门禁的手段）

- 禁止 `-Dmaven.test.failure.ignore=true`、`@Disabled`、删除测试或修改断言来"变绿"。
- CI 配置的每次修改必须经 PR 评审；教师会检查 ci.yml 的提交历史。

## 后果

- 正面：develop 始终在"当前 Sprint 范围内"保持绿色，分支保护持续有效；每个 Sprint 结束时的增量可运行、可演示；集成测试在 S3 集中打通，为 S4 留出缓冲。
- 负面：测试范围需要人工维护，存在"忘了扩大范围"导致回归漏检的风险；因此把本决策写入 ADR，并在每个 Sprint 评审会核查门禁范围是否已按 8.3 节推进。
- 演进路径：S3 全量门禁启用后，本 ADR 状态改为"已完成"，仅保留红线条款作为长期约定。

## 被否决的替代方案

- **一开始就全量硬门禁**：develop 长期红灯，无法合并，协作流程瘫痪。
- **关闭状态检查**：失去 CI 意义，回归无法被自动发现。
- **用跳过测试参数"变绿"**：篡改门禁语义，属学术红线。
