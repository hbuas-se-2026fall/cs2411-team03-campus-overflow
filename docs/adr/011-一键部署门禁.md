# ADR-011：把「一键部署」做成 CI 门禁

**状态**：Sprint 4 已完成 ｜ **驱动特征**：可部署性、可观测性（PB-46 / PB-44）

## 背景

到 v1.0.0 为止，「一键部署」一直只是一句写在文档里的话：`deploy/docker-compose.yml` 从提交第一天起就没有被任何自动化验证过。它有问题时只有两种表现——要么演示当天有人手工 `up -d` 才发现，要么根本没人发现。这带来两个具体后果：

1. **编排文件可以悄悄坏掉而没人知道**。多阶段 Dockerfile、健康检查的 `depends_on: service_healthy`、`.env` 默认值、nginx 转发，任何一处改错都不会让 CI 变红：CI 只跑 `mvn` 和 `npm`，跑不到容器层。
2. **「集成测试是绿的」曾经是假象**。S3 之前 `.github/workflows/ci.yml` 的集成测试步骤挂着 `continue-on-error: true`。真实情况是托管 runner 的 Docker 引擎要求 API ≥ 1.40，而 Testcontainers 内置的 docker-java 默认发 1.32，`CampusOverflowFlowIT` 每一步都是 ERROR，但步骤结论被上报为 success。也就是说端到端从来没有真正在 CI 上跑过，而看板上是绿的。这个教训的通用形式是：**一条没有真正执行的检查，比没有检查更危险**。

两件事合起来指向同一个缺口：项目把「能部署」当作声明而不是事实，缺少一条把声明变成可验证事实的流水线环节。

## 决策

新增 `deploy` job：**只在 `main` 的 push 上触发**，真实地 `docker compose up -d --build` 起全栈，并断言三件事：

| 步骤 | 断言 | 失败含义 |
| --- | --- | --- |
| 校验编排文件 | `docker compose config` 退出码 0 | 编排文件语法或变量引用已坏 |
| 一键部署 | `up -d --build` 退出码 0 | 镜像构建或依赖启动失败 |
| 后端就绪 | `/actuator/health/readiness` 在 ≤ 300 秒内返回 200 | 应用起不来或连不上 MySQL/Redis |
| 前端与演示数据 | `GET /` 返回 200；`/api/v1/questions` 至少 3 条 | nginx 转发断了，或 demo profile 的种子数据没写入 |
| 收尾 | `down -v`、失败时导出容器日志 | — |

四条边界条件：

1. **只在 main push 上跑**，不在 PR 上跑。PR 已经由 backend / frontend / images 三个 job 覆盖；把完整镜像构建周期塞进每个 PR 会让反馈时间翻倍，而 PR 阶段的编排改动由 `docker compose config` 在本地与评审中把关。
2. `needs: [backend, frontend]`：单元测试和类型检查先过，再花时间起容器。
3. **同一份编排文件**（`deploy/docker-compose.yml`）即生产部署入口，不存在「CI 用一套、部署用另一套」的漂移。
4. 演示数据断言 `≥ 3` 条问题，是因为 `prod,demo` profile 确实写入 3 条演示问题——断言故意贴着真实种子数据写，种子改了 CI 会红，迫使改动者同步更新断言而不是把断言放宽。

配套的可观测性决策见 [ADR-012](012-可观测面板provisioning.md)：Grafana 面板同样改为随 compose 自动 provisioning，与「一键部署」共用同一份编排。

## 后果

- **正面**：`main` 上的「能部署」从一句声明变成每次合并都被验证的事实；编排文件坏掉、镜像构建坏掉、健康检查写错、demo 数据没写进去，都会在合并后几分钟内暴露。发布说明里不再需要「请自行 `up -d` 验证」这类话。
- **负面**：`main` 的反馈时间变长——多一个需要构建两个镜像并起五个容器的 job，冷缓存下通常数分钟。这是刻意接受的代价：这个 job 只在 `main` 上跑，且 `needs` 让它在编译与前端已绿之后才开始。
- **运维约束**：`deploy` job 需要 runner 能拉取 Docker Hub 镜像并分配端口 80/8080/3306/6379。组织 runner 配额或网络策略变化会直接表现为该 job 红——这时应当修环境，而不是给步骤加 `continue-on-error`（见 ADR-009 的红线条款）。
- **演进路径**：若后续引入多环境（staging/prod），`deploy` job 的职责收窄为「编排可启动」，环境差异由 `--env-file` 承担；Grafana/Prometheus 的 observability profile 也应纳入该 job 的冒烟范围（当前仅断言应用侧）。

## 被否决的替代方案

- **只在发布说明里写「请自行验证部署」**：这正是本 ADR 要消灭的形态。声明不是验证，且失败成本落在最不该承担的人身上（演示当天的演示者）。
- **每个 PR 都跑完整部署冒烟**：反馈时间与资源消耗翻倍，而 PR 阶段的编排风险已由 `docker compose config` 与代码评审覆盖，收益不对称。
- **给部署步骤加 `continue-on-error` 让它「先跑起来」**：等于回到 S3 之前那个「绿但没跑」的状态，是本 ADR 的直接反面教材。
- **用 Testcontainers 替代 compose 冒烟**：Testcontainers 验证的是「Java 能连上容器化的 MySQL/Redis」，验证不了 nginx 转发、`.env` 默认值、健康检查编排与服务启动顺序——而这些恰好是一键部署最容易坏的部分。
